# Статистика сканов и повторные проверки

Сейчас Reactive — статические файлы на GitHub Pages. Отдельного сервера, базы и бота нет. Этот документ описывает, как позже собрать две вещи, которых в приложении намеренно нет.

1. Статистика для владельца: сколько сканов в день, сколько людей, какие монеты смотрят чаще.
2. Повторные снимки проверенных монет через 1 час, 6 часов, 24 часа и 7 дней, чтобы со временем видеть, что происходит с монетами с похожими флагами.

Пока этого нет в коде. Не пишем сканы в `localStorage` и не ходим за ценой «потом», пока приложение открыто. Такой журнал врёт: он видит только одно устройство и только пока вкладка жива.

## Уведомления уже на клиенте

Сторож не шлёт пуши и не имеет воркера. События считаются в браузере, когда открыт Список: падение скора, падение ликвидности, падение цены, низкий скор, сделки кошельков.

Лимиты тоже стоят здесь, потому что другого места нет:

- Free: слежка за 3 монетами из списка и не больше 8 новых уведомлений в сутки. Типы только «скор упал» и «ликвидность упала».
- Premium: все типы, без потолка по монетам и по числу событий.

Порог (на сколько пунктов упал скор, какой процент ликвидности и цены) хранится в `tc.alertPrefs` на устройстве. Одно и то же событие в один день не считается дважды.

Когда появится сервер, эти же числа надо проверять там, где уведомление реально уходит человеку. Клиентский лимит легко обойти, открыв приложение в другом браузере. До сервера это честный потолок для одного устройства, и в интерфейсе он написан прямо.

## Что должно получиться

Человек проверяет монету. Приложение один раз отправляет на сервер короткую запись. Сервер запоминает монету и ставит четыре будущие проверки. Позже по расписанию он сам спрашивает публичные источники (DexScreener, при необходимости Rugcheck) и кладёт снимок: цена, капитализация, ликвидность, скор.

Владелец открывает закрытую страницу или команду бота и видит сводку за день. В результате монеты, когда данных уже достаточно, может появиться строка вроде: «Монеты с похожими флагами через 24 часа: медиана цены −18%, n=40». Если таких монет мало, строки нет.

Для монеты, которую уже снимали раньше, рядом можно показать «с первой проверки: цена −12%, скор 71 → 54».

## Приватность

В запись не кладём имя, username и сам Telegram id.

Берём числовой id из `Telegram.WebApp.initDataUnsafe.user.id` и храним только хеш. Нормальный вариант: HMAC-SHA256 с секретом, который живёт только на сервере. Голый SHA256 от id тоже лучше, чем открытый id, но его проще перебирать, потому что id — короткое число. Секретный ключ это закрывает.

Если человека нет (проверка не из Telegram), пишем `anon` и не пытаемся склеивать его с кем-то. Адрес монеты не секрет: он и так публичный. Не пишем сумму сделки, адрес кошелька пользователя и текст его собственной проверки.

Срок хранения имеет смысл ограничить, например 90 днями для сырых сканов. Сводки по дням можно держать дольше.

## Модель данных

Минимальные таблицы.

**scans** — каждый запуск проверки, включая повтор той же монеты.

| поле | смысл |
| --- | --- |
| id | свой ключ |
| at | время, unix ms |
| mint | адрес монеты |
| user_hash | хеш tg id или `anon` |
| kind | `reactive` или имя своей проверки |

**coins** — одна строка на монету, первый снимок.

| поле | смысл |
| --- | --- |
| mint | адрес |
| first_at | когда впервые увидели |
| price, mc, liq, score | на первый скан |
| flags | короткие метки: `thin`, `top10`, `mint`, `honey` и т.п. |

**snaps** — последующие точки.

| поле | смысл |
| --- | --- |
| mint | адрес |
| due_at | когда должны были снять |
| at | когда сняли на самом деле |
| price, mc, liq, score | значения |
| ok | удалось ли спросить источник |

**jobs** — очередь, если не хотим сканировать таблицу монет каждый раз.

| поле | смысл |
| --- | --- |
| mint | адрес |
| due_at | +1ч, +6ч, +24ч или +7д от первого скана |
| done | снято или нет |

Флаги на первый скан считаются теми же правилами, что и в приложении: тонкий пул, высокая доля топ-10, открытый минт, honeypot. Список лучше зафиксировать в одном месте, чтобы строка «похожие флаги» не разъехалась с тем, что человек видит на экране.

## Расписание

От `first_at` ставим четыре задачи: +1 час, +6 часов, +24 часа, +7 дней.

Воркер просыпается каждые 5–10 минут, берёт пачку просроченных задач (например 20) и спрашивает DexScreener. Полный скор с Rugcheck дороже и чаще упирается в лимиты, поэтому на повторных точках достаточно цены, капитализации и ликвидности. Скор можно пересчитывать реже, на +24ч и +7д.

Если источник не ответил, задачу сдвигаем на 15–30 минут, не больше трёх раз. Потом помечаем `ok=false` и не долбим адрес весь день.

Пока приложения нет в сети, телефон ничего не доснимает. Поэтому расписание живёт на сервере, а не в `setInterval` на вкладке.

## Строка про похожие флаги

Берём снимки, у которых `at - first_at` попадает в окно 20–30 часов. Группируем по точному набору флагов первой проверки. Считаем медиану изменения цены.

Показываем строку только если в группе не меньше 20 монет. Меньше — прячем. Двадцать — стартовый порог, чтобы одна случайная монета не выглядела как статистика. Текст нейтральный: медиана и число наблюдений, без «покупай» и «продавай».

Та же выборка даёт «с первой проверки» для конкретной монеты: сравниваем текущие цену и скор с `coins`, если первый снимок уже есть.

## Экран владельца

Отдельный URL или команда бота, не пункт в обычном Профиле.

Доступ: список хешей владельца или один секрет в заголовке. Внутри — сегодня и 7 дней:

- сканы;
- уникальные `user_hash`;
- уникальные монеты;
- топ монет по числу сканов;
- сколько повторных снимков снято и сколько сорвалось.

Без сырых id. Экспорт CSV по желанию, не обязателен в первой версии.

## Три способа собрать

### Cloudflare Worker + D1 и KV

Worker принимает `POST /scan`, cron по `*/10 * * * *` забирает очередь. D1 — таблицы выше. KV — секрет HMAC и кэш ответа DexScreener на 1–2 минуты, чтобы пачка одинаковых монет не била API.

Плюс: дёшево на старте, расписание уже есть, не надо держать машину. Минус: D1 имеет лимиты на размер и на число запросов, схему лучше держать простой.

Ориентир по деньгам: бесплатный или очень дешёвый уровень, пока сканов меньше десятков тысяч в день. Сверх этого — единицы долларов в месяц, не сервер за $20.

По работе: один человек, несколько вечеров. Контракт `POST /scan`, cron, одна закрытая страница со сводкой.

### Supabase

Postgres и встроенный REST. Очередь — таблица `jobs` и функция по расписанию (или внешний cron, который дергает Edge Function).

Плюс: привычный SQL, проще смотреть данные руками. Минус: расписание и секреты надо собрать аккуратнее, чем у Cloudflare, где cron — часть того же проекта.

Ориентир: бесплатный тариф на старте, дальше около $25 в месяц, если упираемся в лимиты. По работе примерно столько же, сколько Worker, если не городить лишние таблицы.

### Маленький VPS

Один процесс (Node) и SQLite или Postgres в Docker. Cron системы вызывает тот же код.

Плюс: нет чужих лимитов, проще отлаживать. Минус: машина, обновления, бэкап. Имеет смысл, только если всё равно нужен бот на том же хосте.

Ориентир: $5–10 в месяц за маленький VPS и полдня на то, чтобы это не умерло без присмотра. Больше возни, чем Worker, при том же результате.

## Что трогать в приложении, когда сервер будет

После проверки монеты — один `fetch` на `POST /scan` с `{ at, mint, user_hash, kind, price, mc, liq, score, flags }`. Хеш считается на сервере: клиент шлёт id только внутри уже проверенного `initData`, а не отдельным полем, которое можно подделать. Так спокойнее.

Строку про похожие флаги приложение спрашивает у `GET /similar?flags=thin,top10` и рисует её, только если ответ не пустой.

Лимиты уведомлений на клиенте остаются как подсказка. Настоящий потолок включается в тот момент, когда сервер начнёт сам присылать сообщения.

До этого момента приложение остаётся статическим. План выше — единственное место, где эта работа описана.
